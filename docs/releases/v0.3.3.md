# PKUDisk v0.3.3

This patch lets mounted reads consume incoming data progressively instead of
waiting for an entire cache range to download.

## Evidence and change

The second Windows capture confirms the directory fix: directory HTTP requests
fell from 396 to 14, and the longest directory open fell from 29.63 seconds to
0.043 seconds. These captures contain different workloads, so the counts are
observations rather than a controlled benchmark.

The remaining long waits were read bodies. Across 28 object GETs, median time
to first body bytes was 0.102 seconds, while median completion took 3.544 seconds.
A 64 KiB read waited 10.67 seconds for a complete 4 MiB range even though bytes
started arriving after 0.48 seconds. Other header reads waited 8–10 seconds for
10–16 MiB ranges.

- Readers now return once their requested bytes arrive. The shared fetch
  continues filling its bounded range, and other readers reuse its prefix or
  wait for their missing bytes without another authorization or GET.
- Reads reaching the range end wait for final size/EOF validation. Only complete,
  verified ranges enter the disk cache; interrupted ranges are discarded.
- Cancelling a waiter leaves a useful shared transfer running. An unused cold
  transfer cancels when its last waiter leaves; a new reader does not join
  abandoned work. Unmount cancels and joins all fills before deleting the cache.
- Existing read sizes, concurrency, cache budget, timeouts and CLI/TUI remain
  unchanged. Larger ranges still use more bandwidth/memory; full image decoding
  remains limited by network throughput. A seek late in a range still waits for
  that position to arrive. The existing read flags tune these tradeoffs.
- Verbose logs mark `requested bytes ready` while the shared range continues.

## Validation and upgrade

An HTTP-server regression sends 64 KiB, withholds the rest of a 5 MiB body, and
requires the small read to return before the suffix is released. Prefix reuse,
full-read validation, cancellation, truncated bodies, abandonment/replacement
and unmount are covered. A native WinFsp mounted-drive regression checks the
same behavior, alongside the existing JPEG/GDI+ and memory-mapping tests.

A live Linux mount round trip passed JPEG decoding, full mapped SHA-256
verification and repeated random reads with one retained 5 MiB range. Cold
decode plus mapping took 0.31 seconds; three warm passes took 0.028 seconds in
that environment. Temporary remote files and the mount cache were removed.
These timings do not predict throughput on another connection. The Windows
Photos GUI itself remains unavailable on CI.

Replace the executable and restart existing mounts.

```sh
pkudisk version
```

For a clean native UTF-8 diagnostic capture from Windows PowerShell 5, redirect
through `cmd.exe` from a local folder:

```powershell
cmd.exe /d /c ".\pkudisk.exe mount P: --verbose 2>mount.log"
```

This avoids PowerShell's error-record wrapping and UTF-16 conversion. Normal
mounts have diagnostics disabled. Saved accounts and official license text
keep their existing format; WinGet remains deferred.
